# Pre-Commit Review

## 适用场景

在以下场景优先使用本 Skill：

- 用户要求“提交前检查 / 提交前自检 / pre-commit review / PR 自检”
- 需要快速判断当前改动是否适合提交或合并
- 需要按统一标准输出问题列表与修复建议

## 检查流程

按顺序执行，避免遗漏：

1. 获取改动上下文（已暂存 + 未暂存 + 新文件），明确改动目标
2. 按五大维度进行检查（见下文 Checklist）
3. 只报告有证据的问题，标注严重级别与影响范围
4. 给出“必须修复 / 建议优化 / 可接受风险”的结论

## 五大 Checklist

### 1) 高内聚 & 低耦合

- [ ] 模块是否聚焦单一业务目标，而不是混入无关职责
- [ ] 是否新增了不必要的跨层依赖（如路由层直连底层实现细节）
- [ ] 是否出现“改一处牵一片”的设计（调用方被迫同步修改过多）
- [ ] 公共接口是否保持稳定，内部实现变更是否被封装

关注信号：
- 一个函数同时处理“业务决策 + 数据访问 + 展示格式”
- 改动引入循环依赖或隐式耦合（全局状态、硬编码路径、魔法常量）

### 2) 数据权威性

- [ ] 每类数据是否有唯一可信来源（Single Source of Truth）
- [ ] 是否出现重复写入、重复缓存且无一致性策略
- [ ] 字段含义、默认值、空值语义在各层是否一致
- [ ] 是否避免由派生数据反向覆盖源数据

关注信号：
- 同一个业务字段在多个表/状态源里可被独立修改
- DTO、数据库 schema、业务对象对同字段定义不一致

### 3) 单一职责原则（SRP）

- [ ] 函数/类/模块是否只做一件事，命名与行为一致
- [ ] 变更原因是否单一（不是为多个目标“顺手”改一堆）
- [ ] 错误处理、日志、鉴权、核心业务是否合理分层
- [ ] 是否避免“巨型函数/巨型文件”继续膨胀

关注信号：
- 函数超过可读边界且包含多个 `if/else` 业务分支簇
- 同一文件同时承载协议解析、业务规则、外部 IO

### 4) 避免过度重构

- [ ] 本次重构是否直接服务当前需求或缺陷修复
- [ ] 是否引入与当前目标无关的大规模改名/搬迁/抽象
- [ ] 是否保持最小必要改动，降低回归面
- [ ] 是否保留兼容层或迁移说明（若影响调用方）

关注信号：
- “为了更优雅”修改大量历史代码但无明确收益
- 先抽象后落地，导致实现复杂度明显上升

### 5) Bug 风险检查

- [ ] 边界条件：空值、零值、并发、重复提交、超时、异常路径
- [ ] 状态流转是否完整（成功/失败/回滚/重试）
- [ ] 错误是否被吞掉，日志是否足够定位问题
- [ ] 关键路径是否有测试覆盖，或至少有人工验证步骤

关注信号：
- 仅改“happy path”，缺少失败路径处理
- 数据写入顺序变化但缺少事务或幂等保障

## 输出格式

输出时使用以下结构：

```markdown
## 提交前检查结果

### 结论
- 状态：可提交 / 有阻塞问题
- 风险等级：低 / 中 / 高

### 阻塞问题（必须修复）
1. [维度] 问题描述
   - 证据：`文件路径` + 关键行为
   - 影响：可能导致的错误或回归
   - 建议：最小修复方案

### 优化建议（可后续处理）
1. [维度] 建议描述
   - 收益：可维护性/一致性/可测试性提升点

### 验证建议
- 必跑测试：
- 建议补充测试：
- 最小人工验证步骤：
```

## 执行原则

- 以“正确性与风险”优先，不做风格争论
- 以“最小必要改动”优先，避免引导无关重构
- 结论必须可追溯到实际改动，不做臆测

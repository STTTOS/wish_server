# Texas 并发与一致性规范

本文用于统一 Texas 服务端在并发场景下的设计取舍，避免每次实现接口都重复争论。

## 1. 总原则

- 写接口优先保证**不写坏**（数据约束正确）；
- 读接口允许**短暂陈旧**（最终一致），由后续刷新/WS 事件修正；
- 一致性目标与业务价值匹配：不要为所有接口强行上重锁和长事务。

## 2. 一致性分级

### A. 强一致写接口（必须）

适用：会改变成员关系、房间状态、对局状态、资金结果的接口。

要求：

- 数据库必须有硬约束兜底（唯一索引 / 外键 / 状态约束）；
- 事务内执行“读-判定-写”关键路径；
- 并发冲突要可预期返回（409 或幂等成功），禁止静默写坏。

典型接口：

- `room/create`
- `room/join`
- `room/quit`
- `room/kick`

### B. 最终一致读接口（默认）

适用：详情、列表、快照类查询。

允许：

- 查询时数据有效，但返回后立刻被其他请求修改/软删；
- 下次刷新与 WS 事件修正最终状态。

典型接口：

- `room/detail`
- `room/list`
- `match/detail`

## 3. 并发控制策略选型

### 3.1 首选：数据库硬约束

优先使用数据库表达业务不变量，应用层只负责映射错误语义。

示例（已落地）：

- `Room.activeOwnerId @unique`
- 含义：同一用户最多一个“有效（未软删）房间”

### 3.2 事务锁（`FOR UPDATE`）适用范围

适合“锁定已存在实体”的并发控制。

示例：

- `room/join` 锁定 `Room` 行再计数/写入成员，防止人数超限并发写坏。

不适合：

- “锁不存在的记录”场景（先查无再插入），这类更应依赖唯一约束。

### 3.3 幂等策略

幂等目标：重复请求与第一次请求具有相同外部效果。

建议：

- 写接口优先实现业务幂等（重复调用返回成功 no-op）；
- 需要时可使用幂等键（请求级），但不能替代数据库约束。

## 4. 错误处理规范（并发相关）

- DB 唯一冲突（如 Prisma `P2002`）：
  - 优先转成业务语义（409 或幂等成功）；
  - 禁止直接透传底层错误给客户端。
- 并发窗口下回查不到目标：
  - 返回中性冲突文案（如“创建冲突，请重试”）或系统错误；
  - 不使用会误导的业务文案。

## 5. Room 模块落地约定

### 5.1 `room/create`

- 约束：`Room.activeOwnerId` 唯一；
- 新建房间时写入 `activeOwnerId = ownerId`；
- 房间软删时必须置 `activeOwnerId = null`；
- 并发命中唯一冲突时：
  - 回查同 owner 的有效房间；
  - 查到则按幂等成功返回 `roomId/roomCode`；
  - 查不到则返回 409（中性文案）。

### 5.2 `room/quit` / cleanup 软删

- 软删房间必须同步清空 `activeOwnerId`；
- 否则会阻塞后续创建，造成假冲突。

## 6. 响应契约（与并发规范配套）

- 成功：HTTP 200 + `{ ok: true, message, data, traceId }`
- 失败：HTTP 非 200 + `{ ok: false, message, details, traceId }`
- 客户端判定成功标准：`status === 200 && ok === true`

## 7. 代码审查检查清单

新增/修改写接口时必须确认：

- 是否有数据库硬约束保护关键不变量；
- 是否在事务里执行关键读写；
- 并发冲突返回是否可预期；
- 是否具备幂等语义（至少 no-op 不破坏状态）；
- 是否补齐软删联动字段更新（如 `activeOwnerId`）。

新增/修改读接口时必须确认：

- 是否明确允许最终一致；
- 是否有必要在客户端通过二次拉取/WS 修正状态。

# 技术评分引擎（Decision Skill Engine）方案

> 状态：**v1 定稿基线**（实施中，见 `decision-skill-engine-impl.md`）  
> 范围：逐决策技术性；决策+结构；**洞牌为脏数据，忽略**  
> 非目标：多人 equity 全表、完整 GTO 一步上线、全量 backfill（另通知）

---

## 1. 目标：用量化还原「这人打得好」的感觉

职业观感里的「打得好」，通常不是「这局赢了」，而是：

1. **该打的点打对了**（位置、牌力、线路）
2. **赔率算得清**（该跟的跟、该弃的弃）
3. **有合适的进攻勇气**（偷盲、cbet、价值施压），不是只会跟注
4. **大错少**（离谱跟注、错误弃牌、尺寸颠倒）
5. **长期结果只作校准**，不当主裁判（好友局方差大）

引擎最终形态：

```
每手每个行动节点 → DecisionSnapshot（落库）
                 → 策略模块给出各行动价值 / 建议
                 → 本节点技术分（EV loss 或规则等价分）
                 → 聚合为「局分 / 人分 / 雷达决策维」
```

现有 L1（Adj 战绩）**不计入技术分**（可作诊断）；本引擎（决策+结构）为 **技术分唯一来源**。

---

## 2. 最终形态总览

| 层级       | 做什么                          | 是否落库                           |
| ---------- | ------------------------------- | ---------------------------------- |
| **记录层** | 每个可评分行动写入不可变快照    | 是                                 |
| **策略层** | 输入快照 → 各行动 EV 或规则建议 | 可版本化缓存，非必须逐节点落库     |
| **评分层** | 相对最优的损失 → 节点分         | 可落库节点分，或可重算只落聚合     |
| **聚合层** | 局 / 用户 / 样本门槛上的技术分  | 是（物化，类似现 PlayerStyleStat） |

**原则：快照契约稳定；策略实现可替换（规则 → 局部 blueprint → 完整 solver）。**

---

## 3. 必须记录什么（落库：DecisionSnapshot）

每条记录 = **一个行动节点上的「局面几何 + 玩家行动」**。  
建议新表（名待定）`DecisionSkillEvent` / `PlayerDecisionSnapshot`。

### 3.1 身份与关联

| 字段                  | 说明                                             |
| --------------------- | ------------------------------------------------ |
| `id`                  | 主键                                             |
| `matchId`             | 手牌 / 牌局                                      |
| `userId`              | 行动者                                           |
| `seq` / `actionIndex` | 本手内顺序，保证可回放                           |
| `createdAt`           | 写入时间                                         |
| `schemaVersion`       | 快照字段版本                                     |
| `strategyVersion`     | 当时用于评分的策略版本（可空：先只记快照后补评） |

### 3.2 局面几何（评分键）

| 字段                      | 说明                                                          | 为何需要                         |
| ------------------------- | ------------------------------------------------------------- | -------------------------------- |
| `street`                  | preflop / flop / turn / river                                 | 阶段策略不同                     |
| `playersInHand`           | 仍在本手人数                                                  | HU vs 多人                       |
| `heroPosition`            | 位置枚举（或 seatIndex + button）                             | 偷盲 / 开池 / 防守               |
| `villainPositions`        | 仍在池中对手位置摘要                                          | 多向压力                         |
| `heroStackBb`             | 有效码（建议对当前对手 min 有效）                             | SPR                              |
| `potBb`                   | 行动前底池                                                    | 赔率、尺寸                       |
| `toCallBb`                | 跟注额（0=可过牌）                                            | pot odds                         |
| `spr`                     | pot 相对有效码                                                | 深浅码打法                       |
| `boardPokes`              | 公牌（可空数组）                                              | 牌面结构                         |
| `boardFeatures`           | 结构化特征 JSON（高张/两高/湿润/同花面…）                     | 规则与日后特征复用               |
| ~~holePokes / holeKnown~~ | —                                                             | **不落库、不评分**（洞牌脏数据） |
| `lineTag`                 | 如 `unopened` / `vs_open` / `as_pfr` / `vs_cbet` / `vs_donk`… | 「当前线路」                     |
| `aggressorUserId`         | 本街进攻方（可空）                                            | cbet / 防守角色                  |
| `actionHistoryDigest`     | 压缩历史（或指向 domain event 偏移）                          | 回放与策略键                     |

### 3.3 行动本身

| 字段                | 说明                                      |
| ------------------- | ----------------------------------------- |
| `actionType`        | fold / check / call / bet / raise / allIn |
| `actionSizeBb`      | 增量或 to 额（约定一种）                  |
| `actionSizePotFrac` | 相对底池比例（下注类）                    |
| `isForced`          | 是否盲注等非自愿（自愿行动才评分）        |

### 3.4 当场可算的赔率派生（建议写入，避免重放漂移）

| 字段                    | 说明                                      |
| ----------------------- | ----------------------------------------- | -------------- |
| `potOdds`               | toCall / (pot + toCall)，toCall=0 则 null |
| `mdfHint`               | 可空；面对下注的粗 MDF                    |
| ~~approxEquity / outs~~ | —                                         | 依赖洞牌，不做 |

> 派生字段可重算；落库是为了 **审计与策略版本无关的稳定回放**。

### 3.5 不落库或另行存的

- 完整对手牌（除非已亮牌且业务允许）— 隐私与体积
- Solver 全树 — 太大；只存 `strategyVersion` + 节点评分结果
- 现有 MatchDomainEvent 磁带 — **仍是权威行动源**；快照是评分投影，不替代磁带

**落库结论：要新增「逐决策快照（+可选节点分）」表；可从 domain event / 结算流投影生成，不要求客户端上报。**

## 4. 算什么（评分管线）

### 4.1 节点级（最终形态）

对每个自愿行动节点：

1. 用 `DecisionSnapshot` 查策略模块
   - **终局**：各合法行动的 EV（或等价价值）
   - **过渡**：规则给出 `bestTier` / `acceptable` / `blunder`
2. 计算损失：
   - `evLossBb = EV(best) - EV(taken)`（有引擎时）
   - 或规则分档映射到伪 EV loss
3. 节点技术分示例：
   - `nodeScore = clamp(100 - k * evLossBb / potBb * 100)`
   - 大锅、深码节点提高 `k`（权重）

分档（对齐常见 trainer 语感，阈值 ≠ 对错）：

| 档         | 含义                   | 感觉上     |
| ---------- | ---------------------- | ---------- |
| Best       | 最高 EV / 主线频率行动 | 打得标准   |
| Correct    | 混合策略内可接受       | 仍算会打   |
| Inaccuracy | 小损                   | 略软       |
| Mistake    | 明显 EV 损             | 这点打差了 |
| Blunder    | 大损                   | 业余感来源 |

### 4.2 建议纳入的技术性维度（还原「打得好」）

按观感优先级（均为可量化；实现可分阶段）：

| 维度            | 输入依赖                              | 评什么                                        |
| --------------- | ------------------------------------- | --------------------------------------------- |
| **D1 赔率纪律** | potOdds, equity/outs, toCall          | 听牌/中等牌是否按价跟弃                       |
| **D2 翻前路线** | 位置, 洞牌, lineTag, 码量             | 开池/3bet/fold/cold-call 是否在表内           |
| **D3 位置进攻** | 位置, lineTag(unopened), 对手倾向可选 | 偷盲勇气与乱偷区分                            |
| **D4 延续压力** | as_pfr, boardFeatures, cbet 与否      | 该 cbet 的面是否打、不该打的面是否停          |
| **D5 防守质量** | vs_cbet, potOdds, 牌力                | 该弃不粘、该加注的半诈唬                      |
| **D6 尺寸质量** | sizePotFrac, SPR, 牌力强弱            | 价值偏小/诈唬偏大等                           |
| **D7 大错抑制** | WTSD 类节点、河牌高价跟               | 「爱跟到底」的单点版                          |
| ~~D8 结果校准~~ | Adj bb/100                            | **不进技术分**（review 已定）；可选雷达诊断轴 |

观感映射：

- 「合适彩池赔率 / 补牌」→ D1
- 「当前位置当前阶段最优路线」→ D2–D5
- 「偷鸡勇气」→ D3（+ 剥削模块可选）
- 「操作合乎行动路线」→ D2–D5 综合

### 4.3 聚合怎么算（人感「总分」）

建议：

\[
\text{HandTech} = \text{加权平均}(\text{nodeScore},\ \text{权重 ∝ 底池与街})
\]

\[
\text{PlayerTech} = \text{手数达标后的 HandTech 滚动}
\]

权重建议（**已定稿方向：不要结果层**）：

| 来源                            | 权重       | 说明                                         |
| ------------------------------- | ---------- | -------------------------------------------- |
| 决策质量（D1–D7 聚合）          | **75–85%** | 主技术性（还原「打得好」）                   |
| 结构健康（现 L2/L4 类频率漏洞） | **15–25%** | 样本级兜底（过松、爱跟到底等）               |
| 结果校准（现 L1 Adj）           | **0%**     | **不计入技术分**；可另作雷达诊断轴，不进总分 |

理由见 §9.3。样本门槛：节点数 / 手数不足时只展示「参考」。

## 5. 策略模块形态（可替换）

```
StrategyProvider.evaluate(snapshot) -> {
  actions: [{ type, sizeBucket, evBb?, tier }],
  source: 'rules' | 'blueprint' | 'solver',
  version: string
}
```

| 阶段 | Provider         | 覆盖                                                |
| ---- | ---------------- | --------------------------------------------------- |
| P0   | 规则表           | 翻前 chart + 河牌/翻牌 pot odds 跟弃 + 简单 cbet 面 |
| P1   | 预计算 blueprint | 高频 HU / BTNvsBB 等                                |
| P2   | 引擎 / solver    | 约定桌型内逐点 EV                                   |

**快照字段在 P0 就必须齐**，否则 P2 无法复用历史数据重算。

## 7. 存储与体积（粗估）

- 假设活跃用户每手均 3 ～ 8 个可评分自愿节点
- 每条快照 ~0.5–2KB（含 JSON 特征）
- 需：按 `matchId`/`userId` 索引；冷数据可归档；允许「只存快照、节点分懒重算」以省写放大

## 8. 非目标 / 明确不做（本方案敲定范围外）

- 多人翻前精确 equity 全表
- 客户端本地评分权威
- 用频率差代替 EV 损失作为唯一对错（混合策略点除外）
- 无洞牌时强行打「牌力精确分」（应降权为频率/线路分）

## 9. Review 决议（2026-10-31）

### 9.1 落库粒度 — 已定

- 每个**自愿行动**一条快照。
- **排除盲注 / 前注等被迫下注**：不评分、默认不写评分快照（或写了也 `isForced=true` 且权重 0）。经验上盲注不是技术决策，计入只会稀释「打得好」的信号。
- 超时代打：当前不存在，不考虑。

### 9.2 洞牌是什么 / 缺失怎么办

- **洞牌（hole cards）**：每人开局拿到的 **两张底牌**（只自己可见，直到摊牌或秀牌）。
- **洞牌缺失**：某手在服务端记录里没有该玩家的两张底牌（未亮牌且未持久化、或历史数据不完整）。
- **处理（已定方向）**：快照仍可写（局面几何 + 行动有值）；**依赖牌力的维（精确赔率跟注、chart 选牌等）降权或跳过**；仅频率/线路类仍可评。`holeKnown=false` 时降低该节点权重。

### 9.3 权重：只要决策 + 结构，不要结果 — 建议采纳

**结论：技术分 = 决策 + 结构，结果（Adj/输赢）不进总分。**

思考：

|          | 保留结果低权           | 去掉结果（推荐）                                                      |
| -------- | ---------------------- | --------------------------------------------------------------------- |
| 观感     | 仍会被「这局运气」拉扯 | 更贴近「看操作像不像会打」                                            |
| 好友局   | 方差大，结果噪声高     | 更稳                                                                  |
| 风险     | 与「技术性」语义打架   | 规则/策略若偏了，分会系统性偏，但可用结构维兜底；长期可靠引擎升级纠正 |
| 战绩去哪 | 混在技术分里           | 雷达可另留「去跑马战绩」诊断，**不叫技术分**                          |

D8 结果校准从技术分移除；D1–D7 + 结构（原 L2/L4 类）保留。

### 9.4 维度 — 已定

D1–D7 + 结构足够；不做 timing。

### 9.5 「延后评分」含义 — 已对齐

不是「对局中实时出分」必须。允许：

1. **对局进行中 / 刚结束**：先落 DecisionSnapshot；
2. **对局结束后异步**（秒～分钟级队列）跑 StrategyProvider → 写节点分 → 更新本局/用户聚合。

你确认「结束后延迟出结果也没问题」→ 采用此模式，避免拖慢结算热路径。

### 9.6 雷达 — 已定

不并存双轴。原 skill / 技术分轴改为 **PlayerTech（决策 + 结构）**。

## 10. 聚合口径（局分 / 总分）

### 10.1 单场（某 match 里某玩家）

\[
\text{MatchTech}(user) = \text{该场该玩家所有可评分节点的加权平均}
\]

权重建议：∝ `potBb`（或街权重 × pot），大锅决策更影响「这场打得好不好」。  
对局详情页：展示该场每位玩家的 MatchTech（及可选节点明细）。

### 10.2 总技术分（跨场）

**推荐：先手后人 — 每手一个 HandTech，再对 Hands 等权平均。**

\[
\text{HandTech} = \text{该手可评分节点加权平均}
\]
\[
\text{PlayerTech} = \text{平均}(\text{HandTech over 达标手数})
\]

| 算法                        | 含义             | 问题                                                   |
| --------------------------- | ---------------- | ------------------------------------------------------ |
| **所有行动点直接平均**      | 河牌多的人节点多 | 被「多街粘锅」手数扭曲                                 |
| **所有场次 MatchTech 平均** | 每场一票         | 短场与长场同权，尚可；但一场多手时应用 **按手** 更干净 |
| **按手等权再汇总（推荐）**  | 每手技术质量一票 | 最接近「长期打得稳不稳」                               |

达标：如有效评分手数 ≥ 50（与现样本门槛同级）。

首页榜 / 雷达技术分 = **PlayerTech**。

## 11. 历史数据能否重算 / 刷多久

### 11.1 可行性

**可以，前提是历史 `MatchDomainEvent`（+ 洞牌/结算）足够重建 Snapshot。**

- 有完整磁带 → 离线 job 投影快照 → 跑同一套评分引擎 → 写回聚合（类似 `backfill:style-stats`）。
- 洞牌缺失的手：按 §9.2 降权，不整手作废。
- 极老、磁带残缺的手：跳过并计数。

### 11.2 耗时（量级，非承诺）

取决于历史 **手数 × 每手节点 × 规则成本**：

- P0 规则评分：单机大致可到 **数百～数千手/秒** 量级（粗估，视 IO）。
- 例：10 万手 × 5 节点 ≈ 50 万节点；若 1k 节点/秒 → 约 **数分钟～十几分钟**；若含重投影事件、DB 写放大，按 **数十分钟～数小时** 预留更稳。
- 上 solver 后重算会慢一个数量级以上，需分批。

### 11.3 策略建议

| 策略                                | 何时                                          |
| ----------------------------------- | --------------------------------------------- |
| **只做增量**（上线后新手）          | 想最快上线、接受旧局无技术分                  |
| **上线后异步全量 backfill**（推荐） | 榜与雷达要历史可比；与 style-stats 同运维节奏 |
| 只刷近 N 月                         | 折中                                          |

推荐：**契约与增量先上，紧跟一次性历史 backfill**；榜注明 `techVersion`，刷完前后分不可混比。

---

## 12. 建议落地顺序

1. 定稿 Snapshot schema + Prisma 迁移
2. 投影写快照（结算后异步；盲注排除）
3. 异步评分队列 → 节点分 → MatchTech / HandTech / PlayerTech
4. 对局详情展示局分；雷达 / 榜切新技术分
5. 历史 backfill job
6. StrategyProvider 预留未来引擎

---

## 13. 一句话定稿

> **技术分 = 决策质量为主 + 结构健康为辅，不含输赢结果；逐自愿行动落 DecisionSnapshot，对局结束后异步评分；局分=该场节点加权均，总分=各手 HandTech 等权均；历史可用磁带重算并建议全量 backfill。**

如无异议，本文件视为 v1 定稿基线。
